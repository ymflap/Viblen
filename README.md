Viblen — ڤيبلن

1. تعريف المشروع

Viblen منظومة سحابية متكاملة لإدارة الأنشطة التجارية ونقاط البيع (POS)، مصممة لتخدم عدة شركات ومتاجر داخل نظام واحد، مع عزل بيانات كل شركة عن غيرها.

الهدف هو بناء منصة قابلة للتوسع تبدأ بإدارة المنتجات والمبيعات والمخزون والفواتير، ثم تتوسع لتشمل الموظفين والفروع والتقارير والاشتراكات وإدارة العملاء.

اسم المشروع الرئيسي: "Viblen"

الاسم العربي: "ڤيبلن"

2. أهداف المشروع

- بناء منظومة احترافية لإدارة الأعمال التجارية.
- دعم تعدد الشركات والمستخدمين والفروع.
- توفير نظام كاشير سريع وسهل الاستخدام.
- إدارة المنتجات والباركود والأسعار والخصومات.
- إدارة المبيعات والفواتير والمرتجعات والمخزون.
- توفير نظام عضويات وصلاحيات للموظفين.
- دعم الخطط والاشتراكات وتفعيل الحسابات وانتهائها.
- تقليل تكاليف التشغيل بالاعتماد على الخدمات المجانية حيثما أمكن.
- تطوير المشروع بالكامل عبر GitHub وGitHub Actions باستخدام الهاتف.
- بناء معمارية تسمح بتغيير مزودي الخدمات مستقبلًا بأقل تعديلات ممكنة.

3. البنية التقنية

Cloudflare Pages — الواجهة

تُستخدم لاستضافة ملفات الواجهة الثابتة، بما يشمل صفحات النظام والمكونات والتصميم والملفات اللازمة للتشغيل.

يجب أن تكون الواجهة متجاوبة مع الهواتف والشاشات الأكبر، وألا تحتوي على مفاتيح سرية أو بيانات اعتماد إدارية.

Cloudflare Workers أو Pages Functions — الخادم

تُستخدم طبقة Backend لتنفيذ العمليات الحساسة والتواصل الآمن مع قواعد البيانات والخدمات الخارجية.

مسؤولياتها:

- التحقق من هوية المستخدم.
- التحقق من الشركة والفرع والصلاحيات.
- تنفيذ قواعد العمل والتحقق من المدخلات.
- معالجة المنتجات والمبيعات والفواتير والمخزون.
- التحقق من الاشتراكات والقيود المرتبطة بها.
- حماية البيانات ومنع الوصول غير المصرح به.

سيُختار Workers أو Pages Functions بعد فحص هيكل المشروع واحتياجات النشر.

Cloudflare D1 — قاعدة بيانات التشغيل

تُستخدم D1 لتخزين بيانات التشغيل التي تحتاج إلى البحث والتحديث المستمر، ومنها:

- المنتجات والأسماء والباركود.
- الفئات والأسعار والتكاليف والخصومات.
- المبيعات وبنود البيع.
- الفواتير والمرتجعات.
- المخزون وحركاته.
- البيانات التشغيلية المرتبطة بالشركات والفروع.

يجب تنظيم قاعدة البيانات باستخدام جداول وعلاقات وفهارس وقيود مناسبة، مع استخدام ملفات ترحيل (Migrations) لتتبع تغييرات المخطط.

Supabase — الهوية والمستخدمون والاشتراكات

يُستخدم Supabase مبدئيًا لإدارة:

- تسجيل الدخول وحسابات المستخدمين.
- الشركات وعضويات المستخدمين.
- الموظفين والأدوار والصلاحيات.
- الخطط والاشتراكات.
- حالة التفعيل وتاريخ الانتهاء.

يجب تحديد مصدر الحقيقة لكل نوع من البيانات، وآلية موثوقة لربط هوية المستخدم بعضويته في الشركة.

لا يجوز الاعتماد على معرّف الشركة المرسل من الواجهة وحده؛ يجب أن يتحقق الخادم من العضوية والصلاحيات قبل السماح بالوصول إلى البيانات.

Cloudflare R2 — الأرشيف والنسخ الاحتياطية

يُستخدم R2 لتخزين الملفات والأرشيفات، مثل:

- تقارير المبيعات المصدّرة.
- الأرشيفات الدورية.
- ملفات النسخ الاحتياطية.
- المستندات والمرفقات المستقبلية عند الحاجة.

تُنفذ عمليات التخزين والوصول عبر Backend آمن، مع إعداد سياسة للنسخ الاحتياطي والاحتفاظ والاستعادة.

R2 مخصص للملفات والأرشيف، وليس بديلًا عن قاعدة البيانات التشغيلية.

4. طبقة التكامل والمزوّدات

يجب تصميم المشروع منذ البداية باستخدام واجهات داخلية موحدة ومحوّلات (Adapters) تفصل منطق التطبيق عن الخدمات الخارجية.

تشمل هذه الطبقة:

- واجهات الوصول إلى المنتجات.
- واجهات المبيعات والفواتير.
- واجهات المخزون.
- واجهات تخزين الملفات والأرشيف.
- واجهات الهوية والعضويات.
- واجهات الخطط والاشتراكات.

يجب ألا تتصل كل صفحة بمزوّد خارجي مباشرة. بدلًا من ذلك، تتعامل الوحدات مع واجهات داخلية ثابتة، ويُنفذ الاتصال الفعلي من خلال المحوّل المناسب.

الهدف هو تسهيل إضافة مزوّد أو استبداله مستقبلًا دون إعادة كتابة النظام بالكامل.

تغيير مزوّد البيانات قد يتطلب محوّلًا جديدًا وترحيلًا للبيانات واختبارات توافق؛ لذلك لا يُفترض أن الانتقال سيكون تلقائيًا أو بلا تكلفة.

5. الوحدات الأساسية

الحسابات وتسجيل الدخول

- إنشاء الحساب وتسجيل الدخول والخروج.
- إدارة جلسات المستخدم.
- التعامل مع انتهاء الجلسة والأخطاء.
- حماية المسارات والعمليات الخاصة بالمستخدمين المسجلين.

الشركات والفروع

- إنشاء ملف للنشاط التجاري.
- ربط المستخدمين بالشركات من خلال العضويات.
- دعم الفروع وفق نطاق الإصدار.
- تحديد صلاحيات المستخدم داخل الشركة والفرع.
- ضمان عدم اختلاط بيانات الشركات.

الموظفون والصلاحيات

- إضافة الموظفين وربط حساباتهم بالشركة.
- تعريف أدوار مثل المالك والمدير والكاشير ومشرف المخزون.
- تحديد العمليات المسموح بها لكل دور.
- التحقق من الصلاحيات على الخادم في كل عملية حساسة.

المنتجات والباركود

- إضافة المنتجات وتعديلها وأرشفتها.
- حفظ الاسم والباركود والسعر والتكلفة والكمية.
- تنظيم المنتجات حسب الفئات.
- البحث بالاسم أو الباركود.
- دعم الخصومات والأسعار الإضافية وفق قواعد العمل.
- منع تكرار الباركود داخل النطاق المحدد.

الكاشير ونقاط البيع

- البحث عن المنتجات.
- تعديل الكميات وحساب الإجماليات.
- تطبيق الخصومات المسموح بها.
- التحقق من الأسعار والصلاحيات على الخادم.
- تأكيد البيع وحفظ تفاصيل العملية.
- منع تكرار تسجيل البيع عند إعادة إرسال الطلب.
- تحديد سياسة المخزون السالب ونفاد الكمية.

المبيعات والفواتير

- تسجيل عمليات البيع وبنودها.
- إنشاء مرجع أو رقم فاتورة.
- عرض تفاصيل الفواتير.
- البحث والتصفية حسب التاريخ والموظف والفرع.
- تصدير التقارير والفواتير عند اعتماد طريقة مناسبة.

المرتجعات

- ربط المرتجع بالبيع الأصلي عند الإمكان.
- التحقق من الكميات والصلاحيات.
- تحديث المخزون والإجماليات وفق السياسة المعتمدة.
- حفظ سجل واضح للمرتجع ومن نفذه.

المخزون

- متابعة الكميات الحالية.
- تسجيل حركات الإدخال والإخراج والتسوية.
- ربط كل حركة بسببها.
- منع التعديلات غير المصرح بها.
- توفير سجل لمراجعة اختلافات المخزون.

التقارير

- ملخص المبيعات خلال فترة محددة.
- تقارير المنتجات الأكثر مبيعًا.
- تقارير المخزون والمرتجعات.
- تقارير حسب الشركة والفرع والصلاحيات.
- تصدير البيانات إلى ملفات عند الحاجة.

الاشتراكات والخطط

- تعريف الخطط ومزاياها وحدودها.
- تسجيل حالة الاشتراك وتاريخ بدايته وانتهائه.
- التحقق من صلاحية الاشتراك على الخادم.
- تحديد الوظائف المتاحة عند انتهاء الاشتراك.
- دعم التفعيل اليدوي مبدئيًا إذا كان مناسبًا.
- إضافة الدفع الإلكتروني لاحقًا بعد تحديد مزود الدفع وإعداده واختباره.

لوحة إدارة المنصة

يمكن تطوير لوحة مستقلة لإدارة الخطط والحسابات وحالات الاشتراك ومتابعة الأعطال، مع فصل صلاحيات إدارة المنصة عن صلاحيات الشركات والعملاء.

6. عزل الشركات وحماية البيانات

العزل بين الشركات شرط أساسي في النظام.

يجب تطبيق الضوابط التالية:

- التحقق من هوية المستخدم في كل طلب محمي.
- التحقق من عضوية المستخدم في الشركة.
- التحقق من صلاحياته في العملية المطلوبة.
- تقييد عمليات القراءة والتعديل والحذف بنطاق الشركة الصحيح.
- التحقق من ملكية السجل قبل تعديله.
- منع الاعتماد على القيم المرسلة من الواجهة دون تحقق.
- اختبار محاولات الوصول إلى بيانات شركة أخرى.
- ضمان عدم تسريب بيانات الشركات عبر البحث والتقارير والتصدير.

يجب تنفيذ ضوابط الأمان في Backend، وليس في الواجهة فقط.

7. الأمان والخصوصية

- عدم وضع المفاتيح السرية داخل ملفات الواجهة أو المستودع.
- حفظ الأسرار في إعدادات المنصات المخصصة لها.
- التحقق من المدخلات على الخادم.
- استخدام HTTPS للخدمات المنشورة.
- تقليل البيانات الحساسة المسجلة في السجلات.
- حماية عمليات تنزيل الملفات ورفعها.
- التعامل الآمن مع تكرار الطلبات وفشل الاتصال.
- توفير سياسة احتفاظ وحذف للبيانات.
- إعداد اختبارات للصلاحيات والعزل بين الشركات.
- نشر سياسة خصوصية تتطابق مع الوظائف الفعلية للنظام.

8. الاختبارات والجودة

يجب أن تشمل الاختبارات:

- حساب الأسعار والخصومات والإجماليات.
- تسجيل المبيعات والمرتجعات.
- صحة تحديث المخزون.
- صلاحيات الأدوار المختلفة.
- عزل الشركات ومنع الوصول المتبادل.
- انتهاء الجلسة والاشتراك.
- التعامل مع أخطاء الاتصال وإعادة الطلبات.
- التحقق من إعدادات الأسرار.
- اختبار النسخ الاحتياطي والاستعادة.
- تجربة النظام على الهواتف والشاشات المستهدفة.

نجاح عملية البناء وحده لا يعني أن النظام آمن أو جاهز للإنتاج.

9. التطوير والنشر

- استخدام مستودع GitHub واحد في البداية.
- تنظيم الملفات حسب الوحدات والمسؤوليات.
- استخدام GitHub Actions للفحص والاختبار والبناء.
- اعتماد تغييرات صغيرة قابلة للمراجعة.
- استخدام ملفات Migrations لتغييرات قاعدة البيانات.
- فصل إعدادات التطوير عن الإنتاج.
- عدم إنشاء ملفات مكررة أو غير مستخدمة.
- عدم إعلان اكتمال أي تكامل قبل إعداده واختباره فعليًا.
- جعل خطوات التطوير قابلة للتنفيذ من الهاتف والمتصفح قدر الإمكان.

- إنشاء مستودع GitHub.
- فحص الملفات الموجودة.
- اختيار تقنية الواجهة وBackend.
- تجهيز هيكل المشروع الأولي.
- إعداد الفحوص الأساسية.

المرحلة الثانية: الأساس التقني

- إعداد الواجهة وBackend.

- إنشاء واجهات المزوّدات والمحوّلات.
- تجهيز إعدادات النشر والأسرار.

المرحلة الثالثة: الحسابات والشركات

- ربط Supabase Auth بالـBackend.
- إنشاء الشركات والعضويات والأدوار.
- اختبار الصلاحيات وعزل البيانات.

المرحلة الرابعة: المنتجات والمخزون

- بناء إدارة المنتجات والباركود والفئات.

المرحلة الخامسة: الكاشير والمبيعات

المرحلة السادسة: التقارير والأرشيف

- إنشاء التقارير الأساسية.
- إضافة التصدير.

- اختبار النسخ الاحتياطية والاستعادة.

المرحلة السابعة: الاشتراكات والإطلاق

- إعداد الخطط والتفعيل والانتهاء.
- إضافة الدفع الإلكتروني إذا تم اختيار مزوده.

11. تقدير عدد الملفات

الأرقام التالية تقديرية وليست التزامًا نهائيًا:

- نموذج أولي: 25–50 ملفًا.
- نسخة أولى عملية: 80–140 ملفًا.
- منظومة متكاملة: 150–280 ملفًا.
- منظومة كبيرة باختبارات ووحدات إضافية: قد تتجاوز 280 ملفًا.

سيُحدد العدد الفعلي بعد فحص المستودع واختيار البنية التقنية. الأولوية لجودة التنظيم وسلامة النظام، لا لزيادة عدد الملفات.

12. التكلفة وحدود الخدمات

الهدف استخدام الخطط المجانية حيثما تكفي، مع مراجعة الأسعار والحدود الرسمية وقت الإعداد والإطلاق.

يجب مراقبة:

- استهلاك Backend.
- حجم قاعدة البيانات وعمليات القراءة والكتابة.
- مساحة الأرشيف ونقل الملفات.
- حدود Supabase والخدمات المستخدمة.
- استهلاك GitHub Actions.
- تكلفة النطاق وخدمات الدفع إن أُضيفت.

لا يُفترض أن الخدمات المجانية غير محدودة، ولا يُوعد المستخدم بميزات تعمل دون اتصال إذا كانت تعتمد على الخادم.

13. قرارات تنتظر الحسم

- رابط مستودع GitHub وإعدادات الخصوصية.
- تقنية الواجهة النهائية.

- التصميم التفصيلي لجداول D1.
- آلية الربط الموثوق بين هوية Supabase وعضوية الشركة.
- الأدوار والصلاحيات.
- إدراج الفروع في الإصدار الأول أو تأجيلها.
- سياسات المخزون السالب والخصومات والمرتجعات.
- ترقيم الفواتير والعملة والضرائب حسب السوق المستهدف.
- الخطط والاشتراكات وطريقة التفعيل.
- مزود الدفع إذا تقرر استخدام الدفع الإلكتروني.
- سياسة النسخ الاحتياطي والاستعادة.
- التحقق النهائي من توافر الاسم والنطاق والعلامة التجارية Viblen.

14. معايير قبول النسخة الأولى

لا تُعتبر النسخة الأولى جاهزة للاستخدام الفعلي إلا بعد التأكد من:

- عزل بيانات الشركات فعليًا.

- تسجيل البيع والفاتورة بصورة متسقة.
- تحديث المخزون بطريقة صحيحة.
- منع الوصول غير المصرح به إلى الفواتير والتقارير.
- منع تكرار عمليات البيع بسبب إعادة الطلبات.
- نجاح اختبارات الصلاحيات والأمان الأساسية.
- حفظ الأسرار خارج المستودع.
- اختبار النسخ الاحتياطي والاستعادة.
- تطابق سياسة الخصوصية مع الوظائف الموجودة فعلًا.

الخلاصة

Viblen منظومة تجارية متعددة الشركات، تستهدف الجمع بين نقاط البيع وإدارة المنتجات والمخزون والفواتير والموظفين والاشتراكات في نظام قابل للتوسع.

تعتمد البنية المبدئية على Cloudflare Pages للواجهة، وCloudflare Workers أو Pages Functions للـBackend، وCloudflare D1 لبيانات التشغيل، وSupabase للهوية والعضويات والاشتراكات، وCloudflare R2 للأرشيف والنسخ الاحتياطية.

تُنفذ هذه البنية تدريجيًا بعد فحص مستودع GitHub الفعلي. هذه الوثيقة تحدد المواصفات والخطة ولا تعني أن الخدمات أو التكاملات قد أُنشئت أو اختُبرت بالفعل.
